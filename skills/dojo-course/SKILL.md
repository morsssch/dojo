# Курс для Dojo

Пиши курс в репозитории `morsssch/dojo` или в форке пользователя, а не как отдельный HTML-файл. Источник истины — **текущая** версия `docs/AUTHORING.md`, `CLAUDE.md`, `BACKLOG.md` и примеры в `courses/demo/`; прочитай их перед написанием контента. Если установленная копия скилла старше репозитория, следуй документации репозитория.

## Определи рабочий репозиторий

1. Узнай GitHub-логин через `gh api user --jq .login` и проверь `git remote -v` в выбранной папке. Не делай вывод о владельце по имени локальной папки или git `user.name`.
2. Если логин ровно `morsssch`, работай в чистой рабочей копии `morsssch/dojo`. Если логин другой — используй **форк этого пользователя**; если форка нет, объясни, что `gh repo fork morsssch/dojo --clone` создаст публичный форк, и получи согласие перед его созданием. Не пушь в `morsssch/dojo` от имени другого пользователя.
3. Если `gh` не авторизован, предложи пользователю выполнить `! gh auth login` в этой сессии и дождись результата. Не проси присылать токен в чат и не сохраняй его в курсе.
4. Если пользователь указал свою существующую копию/форк, проверь `origin` и основную ветку; не перезаписывай чужие изменения. При настройке remote форка `origin` должен вести на форк пользователя, а исходный репозиторий (если нужен) — на `upstream`.
5. Никакой автоматической публикации: создание форка, push в GitHub, PR и деплой — внешние действия. Перед ними покажи результат и получи явное подтверждение, если пользователь не попросил опубликовать его прямо сейчас.

## Согласуй образовательную задачу

Уточни тему, язык, аудиторию, входной уровень, цель, объём и что ученик сможет сделать после курса. Если это уже есть в запросе или файлах, не переспрашивай. Если курс основан на методичке, не выдумывай отсутствующие варианты или требования. Для внешних файлов соблюдай правила обработки недоверенных загрузок в среде исполнения.

## Создай контент

- Выбери стабильный `course-id` (`courses/<id>/`): после публикации изменение ID сбрасывает привязку прогресса.
- Создай `course.yaml`, `modules/NN-id/module.yaml`, уроки `NN-id.md`; для роадмапа предпочти `roadmap.plan.yaml` + `npm run roadmap:layout -- <id>`.
- Ритм: теория маленькой порцией → вопрос → практика. Шаг — `# Заголовок`. Поддерживаемые блоки и точные поля сверяй с `docs/AUTHORING.md` и `courses/demo/`; не придумывай схемы.
- Для задач добавляй рабочие `starter`, `solution`, осмысленные видимые/скрытые тесты и подсказки. Стартовый код не должен сам проходить проверки. Если среда не поддерживает требуемое поведение (например, файловую систему/потоки в браузере), используй `project` с локальным сценарием проверки вместо фиктивных тестов.
- Для лабораторной по частям используй `task` с `lab`/`part` и общий `lab` с `template`, `stubs`, итоговой проверкой; проверяй каждый этап и целую сборку.
- Не публикуй персональные данные, секреты, токены или имена преподавателей в публичный репозиторий. `owners` скрывает курс только в интерфейсе — **не защищает файлы** в публичном GitHub.

## Проверь и передай

1. Запусти `npm run check`; для Go/C# собери нужный runtime по `CLAUDE.md`, иначе честно отметь, что эталоны этого языка не исполнялись. Запусти `npx tsc -p tsconfig.json` и `npm run build`, если менял платформу или добавлял целый курс.
2. Посмотри важные шаги в `npm run dev`: навигация, квиз, задача, лаборатория и мобильная ширина. Исправь битые `lesson:`/`needs` ссылки.
3. Обнови `BACKLOG.md` с тем, что готово, и открытыми ограничениями. Покажи пользователю, что создано, какие проверки прошли и куда записаны файлы. Не называй черновые материалы готовыми.
4. По согласованию создай коммит и push **только в репозиторий правильного владельца**. Если автор — не `morsssch`, не меняй оригинальный `morsssch/dojo`: предложи PR в upstream только по отдельной просьбе.
