# Статья и интерактивный материал для Dojo

Статьи живут отдельно от курсов в `articles/<article-id>/`. Перед работой прочитай текущие `CLAUDE.md`, `BACKLOG.md`, `docs/AUTHORING.md` и существующие статьи/примеры в репозитории. Сверяйся с кодом `src/core/articles.ts`, `src/components/InteractiveFrame.tsx` и `tools/check.ts`: формат может меняться.

## Репозиторий и права

1. Узнай логин через `gh api user --jq .login`, затем проверь `git remote -v`. Локальное имя и `git config user.name` не являются доказательством владельца.
2. Логин `morsssch` → работай в копии `morsssch/dojo`. Другой логин → работай только в форке этого пользователя; при отсутствии форка предложи `gh repo fork morsssch/dojo --clone` и спроси подтверждение. Никогда не пушь материалы другого автора в оригинальный `morsssch/dojo`.
3. Если `gh auth` не настроен, предложи `! gh auth login`; не проси токены в чате и не записывай их в файлы.
4. Push, PR, создание форка и деплой — внешние действия. Перед ними покажи diff/результаты и получи явное подтверждение, если пользователь не поручил публикацию явно.

## Формат статьи

Создай:

```text
articles/<article-id>/
  article.yaml
  index.md
  interactive/       # только если действительно нужны интерактивы
```

`article.yaml` должен содержать минимум `title`; обычно также `subtitle`, `description`, `tags` и `draft`. В `index.md` используй Markdown и декларативный блок:

````markdown
```interactive
id: unique-demo
module: ./interactive/demo.ts
props:
  example: basic
```
````

Точные поля проверяй по актуальному парсеру. Не вставляй сырой `<script>` или произвольный JS в Markdown.

## Перенос материала

1. Если источник — PDF/HTML/архив, сначала извлеки и изучи его в изолированной временной папке; не запускай код из загруженной папки как доверенный. Сохраняй все существенные разделы, определения, примеры, ограничения и ссылки, а не только краткое резюме.
2. Сохрани авторскую структуру: оглавление/заголовки, последовательность объяснения, формулы, таблицы и практические разборы. Явно отмечай, если часть источника не перенесена.
3. Сложные схемы и симуляторы делай интерактивным модулем только при наличии реальной пользы: шаги, параметры, таблицы, графики или вычисления. Статичную схему оставляй Markdown/SVG.
4. Интерактивный модуль должен экспортировать/запустить ожидаемый entry point текущего runtime, рисовать только внутри `#app`, ждать `dojo:init`, а высоту сообщать через `postMessage` с `dojo:resize`. Не используй `localStorage`, cookies, токены, DOM родительского приложения или сеть без явной поддержки платформы.
5. Помни, что модуль запускается в sandboxed iframe. Текущий runtime загружает исходный `.ts` как текст и вставляет его в `<script type="module">`: пиши JavaScript-совместимый код без TypeScript-синтаксиса и импортов. Успешный `npm run build` не доказывает, что интерактив исполняется — проверяй его в браузере.
6. Если материал большой, разбивай его на осмысленные `#`/`##` разделы, но не теряй исходный смысл ради сокращения.

## Проверка и передача

1. Запусти `npm run check`, `npx tsc -p tsconfig.json` и `npm run build`. `tools/check.ts` должен ловить отсутствующие `article.yaml`, `index.md`, интерактивные модули и ошибки формата.
2. Проверь статью визуально в dev-сервере: открытие с главной, все интерактивы, кнопки шагов, resize, светлая/тёмная тема, отсутствие ошибок консоли.
3. Обнови `BACKLOG.md`: что перенесено, какие исходники использованы, что осталось. Не называй статью полной, если перенесена только выжимка.
4. Покажи пользователю список файлов, источник и проверки. Коммит/push делай только после согласования и только в репозиторий автора; внешний автор получает изменения в своём форке.
