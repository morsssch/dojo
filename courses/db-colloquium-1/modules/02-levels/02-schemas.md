# Чертёж не равен зданию

Допустим, мы описали таблицу `Книга(номер, название, год)` и правило «номер уникален». Это **схема** — относительно устойчивое описание структуры и ограничений. Сегодня в таблице 120 книг, завтра 121: это **экземпляр (состояние) БД**, то есть конкретные данные в конкретный момент. Добавление книги меняет экземпляр, но не схему; добавление столбца `жанр` меняет схему.

**План БД** в конспекте — проектное описание того, какие объекты, атрибуты и связи должны быть в базе и как они организованы. Слово может использоваться неодинаково: не путай проектный план/схему с *планом выполнения SQL-запроса*, где выбираются операции поиска и соединения. На коллоквиуме важно уметь перейти от потребностей предметной области к структуре и затем отличить её от текущего наполнения.

Три уровня дают несколько видов схем: общую концептуальную, внутреннюю и **внешние схемы (схемы представлений)** для отдельных групп пользователей. Например, схема представления «мои выдачи» может включать название книги и срок возврата, но не чужой адрес. Представление — это способ описать доступный вид данных, а не обязательно отдельная физическая копия строк.

```quiz
id: schema-state
kind: match
question: Сопоставь действие и изменяемое описание.
pairs:
  - { left: Добавили одну выдачу, right: Экземпляр БД }
  - { left: Ввели обязательный атрибут срок возврата, right: Концептуальная схема }
  - { left: Ускорили поиск новым индексом, right: Внутренняя схема }
  - { left: Скрыли адреса в виде для читателя, right: Внешняя схема }
explain: Записи — состояние; структура, хранение и доступные виды — разные схемы.
```

# Как концептуальная модель влияет на остальные

При проектировании сначала решают, что вообще нужно описывать: книги, экземпляры книг, читателей, выдачи и их связи. Это выбор **концептуальной модели**. Реляционная модель предполагает отношения с атрибутами и ключами; иерархическая организует записи по принципу родитель — потомок; ER-модель удобна для анализа предметной области до реализации. От выбора логической структуры зависят возможные внешние виды и способы построения внутренней схемы, но они не обязаны совпадать дословно.

Например, внешний экран «книги читателя» собирает сведения о читателе, выдаче и книге в один удобный список, хотя концептуальная схема разделяет их. Физически эти данные могут лежать в разных страницах и индексах. Так три уровня связаны, но не тождественны.

```quiz
id: view-copy
question: Пользователь видит единый список «название книги — срок возврата». Обязана ли концептуальная схема хранить эту пару в одной таблице?
options:
  - text: Да, экран всегда копирует структуру хранимых таблиц
    why: Внешний вид может объединять сведения из нескольких логических объектов.
  - text: Нет, представление может собирать данные из разных отношений
    correct: true
  - text: Да, потому что представление — это файл на диске
    why: Представление не обязано быть самостоятельным физическим файлом.
explain: Внешняя схема описывает нужный пользователю вид, а не предписывает форму хранения.
```

## Вопрос 6. Влияние моделей концептуального уровня на проектирование БД

Концептуальная модель определяет общую структуру предметной области: объекты, их свойства, взаимосвязи и ограничения без привязки к конкретному хранению. Благодаря разделению уровней и отображениям можно менять физическую реализацию, сохраняя логическую структуру, а совместимые изменения концептуальной схемы — скрывать от внешних приложений. Например, отдельно выделив книгу и факт выдачи, можно построить разные представления для читателя и сотрудника, а затем выбрать индексы независимо от этих представлений. Независимость даёт архитектура с отображениями, а не сама по себе любая нарисованная модель.

## Вопрос 7. План БД, схемы и экземпляры. Основные определения

План БД — проектное описание типов объектов, связей, архитектуры и реализации системы; это не план выполнения SQL-запроса. Схема БД описывает её структуру на определённом уровне абстракции: внешнем, концептуальном или внутреннем. Экземпляр БД — совокупность данных в конкретный момент времени.

Хранимое поле — элементарная единица хранимых данных; хранимая запись — совокупность связанных полей одного типа; экземпляр записи — конкретные значения этих полей; хранимый файл в учебной терминологии — совокупность экземпляров записей одного типа. Например, «Книга(id, название)» задаёт структуру, «(7, Атлас)» — экземпляр записи. Добавление книги меняет состояние БД, добавление атрибута «год» — схему. Реальное размещение записей по файлам зависит от СУБД.

## Вопрос 8. Схемы уровня представлений

Внешняя схема, или схема уровня представлений, описывает вид данных и интерфейс доступа для отдельной группы пользователей. Она обычно включает часть концептуальной схемы и может переименовывать атрибуты, объединять данные и скрывать ненужные детали. Несколько внешних схем могут отображаться на одну общую концептуальную схему. Например, читателю доступны названия его книг и сроки возврата, сотруднику — выдачи всех читателей. Представление не обязано быть физической копией данных и не тождественно экрану приложения.

## Вопрос 13. Влияние концептуальной схемы на внешнюю и физическую модели

Концептуальная схема задаёт общую семантику, структуру и ограничения БД. Внешние схемы получают нужные пользователям виды через отображения на неё, а внутренняя схема реализует хранение этих данных и доступ к ним. Средства DDL позволяют записать структуру и ограничения в терминах выбранной модели. Например, концептуальные Читатель, Книга и Выдача образуют внешний список «мои книги», а физически реализуются страницами, файлами и индексами. Качественная концептуальная схема облегчает получение корректных представлений и реализацию, но не диктует единственное физическое размещение.
