# Как писать курсы для Dojo

Инструкция для автора — человека или нейронки. Её достаточно, чтобы написать курс целиком, не читая код платформы.
Живые примеры каждого блока — в `courses/demo/` (курс «Витрина Dojo»). Если сомневаешься, как что-то записать, открой его.

---

## 0. Короткий чек-лист

1. Создай/найди папку курса `courses/<course-id>/`.
2. Пиши уроки в Markdown: шаг = заголовок `# ...`, задания = fenced-блоки (`quiz`, `task`, `git`, `anim`, `project`, `cards`, `written`, `lab`).
3. Запусти `npm run check` — он валидирует YAML и **прогоняет эталонные решения всех задач**. Ноль ошибок — можно коммитить.
4. Посмотри урок глазами: `npm run dev` → http://localhost:5173.
5. Обнови статус урока (`draft: false`) и бэклог курса, если он есть.

## 1. Структура файлов

```
courses/
  <course-id>/                 # id курса = имя папки (латиница, kebab-case)
    course.yaml                # метаданные курса
    roadmap.yaml               # роадмап (необязательно)
    modules/
      01-go-basics/            # порядок — по числовому префиксу; id модуля = "go-basics"
        module.yaml
        01-hello.md            # урок; id = "hello", ключ урока = "go-basics/hello"
        02-variables.md
      02-sql/
        ...
```

- **Порядок** модулей и уроков задаётся только числовым префиксом (`01-`, `02-`, …). Перенумеровать можно свободно —
  прогресс учеников привязан к id *без* префикса.
- **Нельзя переименовывать id** (часть имени после префикса) у уже опубликованных уроков: прогресс учеников потеряется.
- Префиксы удобно делать с запасом (`010-`, `020-`), чтобы вставлять уроки между.

### course.yaml

```yaml
title: Go Backend с нуля
subtitle: Одна строка под заголовком
icon: 🐹                     # необязательно
order: 1                     # порядок на главной
draft: false                 # true — курс виден только в dev-режиме
owners: [login]              # необязательно: личный курс — на сайте виден только после входа синхронизацией
                             # под этим логином GitHub (не защита: файлы всё равно в публичном репозитории)
description: |               # markdown, показывается на странице курса
  Для кого курс и что будет в конце.
belts:                       # необязательно: свои уровни. По умолчанию — пояса дзюдо
  - { at: 0, name: Белый пояс, color: '#eef0f4' }
  - { at: 0.5, name: Синий пояс, color: '#3d7be0' }
variants:                    # необязательно: варианты (см. раздел 8⅞)
  label: Вариант             # как называть выбор: «Вариант», «Стек», «Язык»…
  options:
    - { id: v1, title: Вариант 1, description: Чётные числа }
    - { id: v2, title: Вариант 2 }
codewars:                    # необязательно: разминка на главной (ссылки на Codewars)
  lang: go                   # язык решения на Codewars: go, python, javascript, sql…
  katas:
    - { slug: 5266876b8f4bf2da9b000362, title: Who likes it?, rank: 6 kyu, after: go-basics }
```

- `codewars.katas[].slug` — id задачи из адреса `codewars.com/kata/<slug>`. Проверь, что задача есть на нужном языке.
- `after` — id модуля: задача попадает в разминку, когда ученик прошёл в этом модуле хотя бы один урок. Без `after` — сразу.
  Задачи не встраиваются в сайт: ученик открывает ссылку, решает на Codewars и отмечает «Решил».

## 2. Шаги урока

Урок делится на **шаги** заголовками первого уровня. Каждый шаг — отдельная «плитка» сверху, как на Stepik.

~~~~markdown
# Что такое слайс          ← шаг 1 (теория)
Текст...

# Проверим                 ← шаг 2 (квиз)
```quiz
...
```

# Под капотом              ← шаг 3
~~~~

Правила хорошего шага:
- **Порция:** 1 идея на шаг, 150–400 слов теории. Длинный текст разбивай на несколько шагов.
- **Ритм:** теория → вопрос → теория → вопрос → задача. После каждого куска теории — хотя бы один квиз.
- Внутри шага используй `##` и `###` для подзаголовков (не `#` — он начинает новый шаг).
- Шаг без заданий засчитывается при открытии. Шаг с заданиями — когда решены все задания в нём.

Тип плитки определяется автоматически по первому заданию в шаге: теория / вопрос / задача / git / схема / проект.

## 3. Теория: Markdown и выноски

Работает весь GitHub-flavored Markdown: таблицы, списки, `код`, ссылки, картинки.

### Выноски

```markdown
> [!NOTE]
> Нейтральная заметка.

> [!TIP] Свой заголовок
> Совет. Текст после метки становится заголовком.

> [!WARNING]
> Типичная ошибка.

> [!DANGER]
> Так делать нельзя.

> [!DEEP]
> «Под капотом» — сворачиваемый блок. Сюда — как устроено внутри: память, планировщик, протокол.
```

`[!DEEP]` — главный инструмент для глубоких объяснений: основной текст остаётся коротким, а желающие раскрывают подробности.

### Код

- Обычный блок ```` ```go ```` — просто подсветка. Языки: go, sql, js/ts, python, bash, json, yaml, dockerfile, http, xml/html, diff, kotlin, nginx, proto.
- **Запускаемый пример:** ```` ```go run ```` (также `sql run`, `js run`, `python run`). Ученик может поменять код и запустить. Без проверки.
- В `sql run` всё, что выше строки `-- ^ setup`, выполняется незаметно (создание таблиц):

````markdown
```sql run
CREATE TABLE t (x int); INSERT INTO t VALUES (1), (2);
-- ^ setup
SELECT sum(x) FROM t;
```
````

### Mermaid

```` ```mermaid ```` — статичные диаграммы (sequence, flowchart, ER, state). Для пошаговых объяснений лучше `anim` (см. ниже).

## 4. Квизы — блок `quiz`

Содержимое блока — YAML. Поля с Markdown: `question`, `options[].text`, `options[].why`, `explain`, `hints`.

```yaml
id: slices-append          # уникален в пределах урока; лучше задавать явно (иначе прогресс привязан к позиции)
kind: single               # single | multiple | text | number | order | match   (по умолчанию single)
question: Что выведет программа?
code: |                    # необязательно — код под вопросом
  fmt.Println(len("привет"))
lang: go                   # язык подсветки code (по умолчанию go)
options:
  - text: "6"
    why: Это количество символов, а len считает байты.   # показывается, если ученик выбрал этот вариант
  - text: "12"
    correct: true
explain: |                 # показывается после верного ответа или после 2 ошибок
  Кириллица в UTF-8 — 2 байта на символ.
hints:                     # открываются по одной кнопкой
  - Чем отличается байт от символа?
```

Виды:
- `single` — один правильный (`correct: true` ровно у одного).
- `multiple` — несколько правильных; ученик должен выбрать все и только их.
- `text` — `answer: "go"`, или список `answer: [go, golang]`, или регулярка `answer: /^\s*select\s*$/i`. Регистр и лишние пробелы игнорируются.
- `number` — `answer: 404`, допуск `tolerance: 0.01`.
- `order` — `options` перечисляются **в правильном порядке**, ученику они показываются перемешанными (перетаскивание мышью/пальцем, кнопки, стрелки).
- `match` — сопоставление: `pairs: [{ left: "`7 / 2`", right: "3" }, ...]`. Правая колонка перемешивается, правые части должны быть разными.

Как писать хорошие вопросы:
- Неверные варианты — **типичные заблуждения**, а не очевидная чушь. У каждого неверного варианта — `why`.
- Вопросы «что выведет код» — лучший формат для Go: заставляют мысленно исполнить код.
- Варианты, начинающиеся с `` ` ``, `[`, `{`, `*`, `-`, или содержащие `: `, **бери в кавычки** (это YAML).

## 5. Задачи с кодом — блок `task`

### Go / JS / Python: ввод-вывод

```yaml
id: sum
lang: go                   # go | js | python | sql
title: Сумма двух чисел
prompt: |                  # markdown
  Прочитай два числа и выведи сумму.
starter: |                 # стартовый код в редакторе
  package main
  ...
solution: |                # эталон: проверяется `npm run check`, ученику показывается после 3 попыток
  package main
  ...
tests:
  - { stdin: "2 3", stdout: "5" }
  - { name: большие числа, stdin: "1000000000 1000000000", stdout: "2000000000", hidden: true }
hints: [...]
explain: |                 # показывается после решения: разбор, альтернативы
```

Сравнение вывода игнорирует пробелы в конце строк и пустые строки в конце.

### Go / JS / Python: проверка функций (харнесс)

Ученик пишет функции (без `main`), скрытый `harness` их вызывает:

```yaml
harness: |
  package main

  func main() {
  	dojoCheck("Reverse([1 2 3])", Reverse([]int{1, 2, 3}), []int{3, 2, 1})
  	dojoAssert("не паникует на nil", Reverse(nil) != nil, "Reverse(nil) вернул nil")
  }
```

- `dojoCheck(имя, получено, ожидалось)` — сравнение через `reflect.DeepEqual` (Go) / JSON (JS) / `==` (Python).
- `dojoAssert(имя, условие, сообщение)` — произвольная проверка.
- Харнесс может импортировать пакеты — импорты склеиваются с импортами ученика автоматически.
- В Python функция называется `dojo_check` (или `dojoCheck`).
- Можно комбинировать `harness` и `tests`.

### HTTP в Go

Сети в браузере нет, но `net/http` + `net/http/httptest` работают: харнесс вызывает хендлер через `httptest.NewRecorder()`.
Пример — `courses/demo/modules/02-practice/01-go.md`, шаг «HTTP-хендлер».

### Требования к коду: `require` / `forbid`

Проверка по тексту решения (комментарии вырезаются). Нужна, когда важно *как* решено, а не только результат:

```yaml
require:
  - ['\bfor\b', 'Нужен цикл for']                      # [regex, сообщение ученику]
forbid:
  - ['slices\.Reverse', 'Сделай сам, без slices.Reverse']
  - { pattern: 'sort\.', message: 'Без пакета sort', flags: 'i' }
```

Не злоупотребляй: регулярка не понимает код. Используй для явных запретов («без готовой функции») и обязательных конструкций.

### «Опирается на»: `needs`

`needs: [go-basics/functions, go-data]` — у задачи (`task`, `git`, `project`) сверху появится плашка со ссылками на уроки, на которых она держится. Непройденные выделены пунктиром. Битые ссылки ловит `check`.

### Объяснения ошибок

Под ошибкой компиляции/выполнения Go и ошибкой Postgres автоматически показывается объяснение по-русски
(«nil map → создай через make», «column does not exist → строки бери в одинарные кавычки»).
Словарь — `src/core/runners/explain.ts`. Встретил частую ошибку без объяснения — добавь паттерн туда.

### Полноэкранный режим

У каждой задачи с кодом и git-задачи есть кнопка «На весь экран»: условие слева, редактор справа, вывод снизу.
Пиши `prompt` так, чтобы он читался в узкой колонке: короткие абзацы, списки, без широких таблиц.

### Ограничения Go в браузере (важно!)

Код выполняет интерпретатор **yaegi**, а не компилятор. Отличия:
- **Не** ругается на неиспользуемые переменные и импорты. Не делай задачи, проверяющие именно это.
- Стандартная библиотека уровня **Go 1.22**: нет `slices.Sorted`, `maps.Keys` как итераторов, range-over-func.
- Вывод типов в дженериках слабее: иногда нужно явно `Map[int, string](xs, f)`. Проверяй эталон через `npm run check`.
- Доступные пакеты: bufio, bytes, cmp, container/heap, container/list, context, crypto/(md5, sha1, sha256, rand, hmac),
  encoding/(base64, hex, json, csv, xml), errors, fmt, hash/fnv, io, io/fs, log, log/slog, maps, math, math/bits, math/rand,
  net/http, net/http/httptest, net/url, os, path, path/filepath, reflect, regexp, slices, sort, strconv, strings, sync,
  sync/atomic, text/template, html, time, unicode, unicode/utf8.
  Нужен другой пакет — добавь в `runtimes/go/build.sh` (`PKGS`) и пересобери (`npm run build:go-runtime`).
- Нет: файловой системы, сети, сторонних модулей (`github.com/...`), `go test`. Для этого — блок `project`.
- Таймаут — 8 секунд. Дедлок не детектится, а ловится таймаутом.

### SQL (PostgreSQL)

```yaml
id: top3
lang: sql
setup: |                   # схема и данные; выполняется перед кодом ученика и эталоном
  CREATE TABLE teams (id serial PRIMARY KEY, name text, place int);
  INSERT INTO teams (name, place) VALUES ('a', 2), ('b', 1);
starter: |
  SELECT
solution: |
  SELECT name FROM teams ORDER BY place LIMIT 3;
ordered: true              # важен ли порядок строк (по умолчанию нет)
check: |                   # для INSERT/UPDATE/DELETE: этот запрос выполняется после кода, сравниваются его результаты
  SELECT * FROM teams ORDER BY id;
```

- Каждая проверка — в отдельной транзакции, которая откатывается. Ученик ничего не может сломать.
- Сравниваются значения, не имена колонок (алиасы не важны). Число колонок — важно.
- Над редактором — блок «База данных»: ER-диаграмма (таблицы, колонки, PK/FK, связи) и вкладки с данными каждой таблицы.
  Схема берётся у Postgres после выполнения `setup`, поэтому объявляй связи через `REFERENCES` — тогда они нарисуются линиями.
- При ошибке ученик видит свой и ожидаемый результат.

## 6. Git — блок `git`

Терминал с настоящим git (isomorphic-git) в браузере, граф коммитов, вкладка «Файлы» с редактором.

```yaml
id: first-commit
title: Первый коммит
prompt: |
  Создай репозиторий в папке app и закоммить README.md.
setup:                     # команды, выполняются молча перед стартом
  - mkdir app
goals:                     # цели отмечаются автоматически после каждой команды
  - text: Есть репозиторий
    check: { repo: true }
  - text: Сделан коммит
    check: { commits: 1 }
solution:                  # эталон — обязателен для `npm run check`
  - cd app
  - git init
  - echo "# app" > README.md
  - git add . && git commit -m "init"
hints: [...]
explain: |                 # после решения
sandbox: false             # true — песочница без целей, не влияет на прохождение
```

**После setup ученик всегда начинает в домашней папке `~` (`/home/student`)**, и `solution` выполняется оттуда же.

### Проверки (`check`)

Все проверки выполняются в репозитории, внутри которого сейчас находится ученик (ищется вверх от текущей папки).

| check | смысл |
|---|---|
| `{ repo: true }` | ученик внутри git-репозитория |
| `{ file: path }` | файл существует; `contains: "текст"` — содержит строку; `absent: true` — файла нет |
| `{ branch: name }` | ветка существует; `exists: false` — ветки нет |
| `{ head: name }` | текущая ветка — `name` |
| `{ commits: N }` | в HEAD (или `branch: x`) не меньше N коммитов |
| `{ message: regex }` | сообщение последнего коммита HEAD (или `branch`) подходит под regex |
| `{ clean: true }` | нет незакоммиченных изменений и незавершённого merge |
| `{ staged: path }` | файл в индексе с изменениями |
| `{ tracked: path }` | файл отслеживается git |
| `{ merged: a, into: b }` | ветка `a` влита в `b` |
| `{ tag: name }` | тег существует |
| `{ remote: origin }` | remote добавлен; с `branch: main` — ветка запушена и совпадает с локальной |

### Сценарии с «удалённым» репозиторием и тиммейтами

Remote — это папка: `git init --bare /srv/origin.git`. В setup можно сыграть за тиммейта в другой папке:

```yaml
setup:
  - git init --bare /srv/origin.git
  - mkdir /petya && cd /petya && git clone /srv/origin.git bot && cd bot && git config user.name Петя && echo x > a.txt && git add . && git commit -m "petya" && git push
  - cd /home/student && git clone /srv/origin.git bot
```

Поддерживаемые команды: `ls cd pwd cat echo (> >>) touch mkdir rm mv tree clear help`, `&&` и `;`.
Git: `init config status add rm commit (-m -a --amend) log (--oneline --all -n) show diff (--staged) restore reset (--soft --hard)
branch (-d -D -m -a) checkout (-b, файлы) switch (-c) merge (--no-ff --abort, конфликты) tag remote clone push (-u -f) fetch pull`.
**Нет:** rebase, stash, cherry-pick, revert, редактора (сообщение коммита — только `-m`).

> [!WARNING]
> Команды в YAML, содержащие `: ` (двоеточие с пробелом, например в сообщении коммита), **бери в одинарные кавычки**,
> иначе YAML превратит строку в объект: `- 'git commit -m "feat: x"'`.

## 7. Анимированные схемы — блок `anim`

Пошаговая анимация: узлы на сетке, по стрелкам летят «пакеты», подсвечиваются узлы, меняются подписи. Лучший способ объяснить
протоколы, жизненный цикл запроса, горутины и каналы, работу индекса, очередь сообщений, кэш.

```yaml
title: Путь запроса
nodes:                     # x, y — клетки сетки (≈170×110 px)
  - { id: client, label: Клиент, x: 0, y: 0, kind: actor }
  - { id: api, label: API, x: 1, y: 0, sub: "ждёт" }          # sub — вторая строка (моноширинная)
  - { id: db, label: Postgres, x: 2, y: 0, kind: db }
  - { id: cache, label: Redis, x: 1, y: 1, kind: box, w: 2 }  # w — ширина в клетках
edges:                     # статичные линии: [from, to] или [from, to, подпись]
  - [client, api]
  - [api, db, "SQL"]
steps:
  - text: Клиент отправляет запрос.            # markdown-подпись шага
    send: { from: client, to: api, label: "GET /users" }      # можно список send — несколько пакетов сразу
    highlight: [client]
  - text: API идёт в базу.
    send: { from: api, to: db, label: SELECT, color: "#4fb477" }
    set: { api: "ждёт БД" }       # поменять sub у узлов (состояние сохраняется на следующих шагах)
  - text: Появляется кэш.
    show: [cache]                # узлы из show скрыты до этого шага
    hide: [db]                   # скрыть узел начиная с этого шага
```

`kind`: `box` (по умолчанию), `actor` (скруглённый), `db` (цилиндр), `cloud` (пунктир), `queue` (с делениями),
`cell` (ячейка памяти), `note` (подсвеченная заметка).

Советы: 4–9 шагов, одна мысль на шаг, подпись шага — 1–2 предложения. Схема не засчитывается как задание.

## 8¾. Лаба по этапам — блок `lab`

Большая программа, которую пишут по кускам. Шаблон программы содержит вставки `{{имя}}`, каждая вставка — отдельный
**этап**: обычная задача `task` с полями `lab` и `part`. Этап проверяется внутри целой программы: предыдущие этапы
берутся из решений ученика, следующие заменяются заглушками из `stubs`. Блок `lab` (обычно последний шаг урока)
собирает всё, прогоняет общие тесты и даёт скопировать или скачать готовый файл — например, для сдачи.

Живой пример — `courses/demo/modules/02-practice/05-lab.md`.

````markdown
```task
id: lab-words
lab: freq          # id блока lab в ЭТОМ ЖЕ уроке
part: words        # имя вставки {{words}} в шаблоне
lang: go           # тот же язык, что у лабы
title: Разбить текст на слова
prompt: Напиши функцию `Words(text string) []string`...
starter: |         # только кусок программы — без package и import
  func Words(text string) []string {
  	return nil
  }
solution: |
  func Words(text string) []string { ... }
harness: |         # своя main у харнесса: main шаблона при проверке этапа убирается сама
  package main
  func main() {
  	dojoCheck("Words", Words("a b"), []string{"a", "b"})
  }
```

```lab
id: freq
title: Счётчик слов
lang: go                       # go | js | python
intro: Что делает программа целиком.
template: |                    # вся программа; вставка, стоящая одна на строке, получает отступ строки
  package main

  import (
  	"fmt"
  	"sort"
  )

  var _ = sort.Ints            // импорт нужен только этапу: заглушки его не используют, а Go ругается

  {{words}}

  func main() { ... }
stubs:                         # код на месте ещё не решённого этапа: компилируется, но ничего не умеет
  words: |
    func Words(text string) []string { return nil }
tests:                         # проверка собранной программы: tests (stdin → stdout) и/или harness
  - { stdin: "a b a", stdout: "a 2\nb 1" }
checklist:                     # необязательно: что ученик отмечает сам
  - Программа собирается из моих этапов
```
````

Правила:
- Импорты пиши в `template`, а не в этапах. Если импорт нужен только этапу, добавь в шаблон `var _ = пакет.Что-то`,
  иначе программа из заглушек не скомпилируется.
- Для каждой вставки нужен этап **или** заглушка. Один этап — одна вставка.
- Ввод в лабах на Go читай через `fmt.Scan` (так работает ввод в браузерном Go).
- `check` проверяет: каждый этап внутри программы (предыдущие — эталонные решения), программу из всех эталонов
  целиком и предупреждает, если программа из одних заглушек уже проходит тесты.
- Лаба засчитывается, когда собранная программа проходит проверку блока `lab`.

## 8⅞. Варианты — блок `variant`

Если у курса есть варианты (`variants` в course.yaml), ученик выбирает свой на странице курса. Содержимое внутри
блока `variant` видят только ученики перечисленных вариантов, а их задания входят в прогресс только для них.
Пока вариант не выбран, показывается первый, и в уроке есть плашка выбора.

Внешний забор — **четыре** обратные кавычки, чтобы внутри можно было писать обычные блоки:

`````markdown
````variant v1
**Вариант 1.** Посчитай чётные числа.

```task
id: var-even       # id блоков разных вариантов должны различаться
...
```
````

````variant v2 v3
Текст и задания для вариантов 2 и 3.
````
`````

- Внутри — что угодно: текст, квизы, задачи, этапы лабы. Вложенные `variant` не поддерживаются.
- Лаба по вариантам: сделай для каждого варианта свой блок `variant` с этапами и своим блоком `lab` (с разными id).
- Неизвестный id варианта — ошибка `check`.

## 9. Урок-чекпоинт

`checkpoint: true` во frontmatter. Это тест по модулю: если решено ≥ `pass` (по умолчанию 0.8) заданий урока,
ученику предлагается отметить **весь модуль** как пройденный. Нужен, чтобы знающие люди быстро проскакивали базу.
Обычно последний урок модуля; 5–10 вопросов на ключевые идеи модуля.

### Экзамен

Отдельной сущности нет: экзамен — это **модуль без теории**, где каждый урок состоит из заданий (`quiz`, `task`, `git`,
`lab`). Сделай последний урок такого модуля чекпоинтом, если сдача должна отмечать предыдущие модули пройденными.

## 9½. Что платформа делает сама

Писать для этого ничего не нужно:
- **Поиск** (Ctrl/⌘+K) — по заголовкам шагов и тексту всех уроков, плюс по заметкам ученика.
- **Заметки** — к любому шагу; выделенный текст урока можно отправить в заметку. Страница «Мои заметки» в курсе.
- **Прогресс, серия, достижения** — считаются по решённым блокам и просмотренным шагам.
- **Синхронизация** — ученик входит своим токеном GitHub, прогресс хранится в его секретном гисте.
- **Варианты оформления** — тема, защита зрения, шрифт, размер, акцент.

Поэтому заголовки шагов делай осмысленными: по ним ищут.

## 10. Роадмап — `roadmap.yaml`

Карта курса в духе roadmap.sh. Узел на карте короткий (только название), а по клику открывается панель: описание,
уроки курса, внешние материалы и кнопки «Изучаю / Готово / Пропустить». Узел зеленеет, когда пройдены все связанные
уроки (или ученик нажал «Готово»).

**Два способа:**
1. **План + генератор (рекомендуется).** Пишешь `roadmap.plan.yaml` — только смысл: темы по порядку, подтемы, проверки.
   Команда `npm run roadmap:layout -- <course-id>` раскладывает его в `roadmap.yaml` змейкой. Координаты не нужны.
2. **Вручную.** Пишешь `roadmap.yaml` с координатами (см. «Узлы» и «Связи» ниже) — для нестандартных карт.

Пример плана — `courses/go-backend/roadmap.plan.yaml`, ручной карты — `courses/demo/roadmap.yaml`.

### roadmap.plan.yaml

```yaml
layout: snake          # snake — ряды по perRow тем, направление чередуется (по умолчанию); straight — одна колонка
perRow: 3              # 2–5 тем в ряду
title: Go Backend      # заголовок над картой (необязательно)
sections:
  - { id: go, title: Язык Go }
topics:                # в порядке изучения
  - id: go-basics
    title: Основы Go
    section: go
    links: [go-basics]                     # модуль или "модуль/урок"
    description: Зачем тема и что внутри.  # markdown для панели
    resources:
      - { title: A Tour of Go, url: 'https://go.dev/tour/', kind: docs }
    group: Синтаксис                       # заголовок рамки с подтемами (необязательно)
    subs:                                  # подтемы — рамкой под темой
      - { id: go-vars, title: Переменные и типы, links: [go-basics/vars] }
      - { id: go-funcs, title: Функции }
    checkpoint: { id: go-cp, title: 'Проверь себя: основы', links: [go-basics/test] }
    optional: false                        # true — тема «по желанию» (пунктир)
```

После генерации карту можно поправить руками, но повторный запуск перезапишет `roadmap.yaml` (в шапке файла
об этом написано). Подписи подтем — до ~28 символов.

### Узлы

```yaml
sections:                       # группы; цвет — маленький маркер в панели узла
  - { id: go, title: Язык Go, color: '#2f9e63' }
nodes:
  - id: go-basics               # уникальный id (латиница)
    kind: topic                 # см. таблицу ниже; по умолчанию topic
    title: Основы Go            # коротко: 1–4 слова, это подпись на карте
    section: go
    x: 470                      # левый верхний угол, px; держи кратным 10
    y: 300
    w: 260                      # ширина (необязательно, есть значение по умолчанию)
    description: |              # markdown для панели: зачем тема, что внутри, как применить на хакатоне
      Переменные, типы, функции...
    links: [go-basics]          # модуль целиком или "модуль/урок"
    resources:                  # внешние материалы
      - { title: A Tour of Go, url: 'https://go.dev/tour/', kind: docs }   # article|video|docs|course|tool|book
    optional: false             # true — пунктирная рамка «по желанию»
```

| kind | как выглядит | размер по умолчанию (w×h) | для чего |
|---|---|---|---|
| `topic` | жирная рамка с тенью | 220×48 | ключевая тема на основной линии |
| `sub` | тонкая рамка, одна строка | 200×40 | подтема/урок сбоку от темы |
| `checkpoint` | тёмная плашка | 260×48 | проект, «проверь себя», финальная работа |
| `label` | просто текст | 240×40 | подпись на холсте («Отсюда начинается бэкенд») |
| `title` | крупный заголовок | 320×56 | заголовок карты/раздела |
| `note` | плашка с markdown (`description`) | 280×90 | пояснение |
| `group` | рамка-подложка под другими узлами, `title` — подпись | 300×160 | объединить подтемы |

### Связи

```yaml
edges:
  - [go-basics, go-data]                                   # коротко: стороны выберутся по положению
  - { from: start, to: go-basics, fromSide: bottom, toSide: top, style: solid }
  - { from: go-basics, to: vars, fromSide: left, toSide: right, style: dotted }
  - { from: a, to: b, via: [[600, 900], [900, 900]] }      # ломаная через точки (центры сторон узлов → via → цель)
  - { from: a, to: c, curve: true }                         # плавная кривая вместо прямых углов
```

- `fromSide` / `toSide`: `top | right | bottom | left` — с какой стороны выходит и куда входит линия.
- `style`: `solid` — основной путь, `dotted` — ответвление к подтеме, `dashed` — альтернатива/необязательное.
  По умолчанию: связи с `sub` и `checkpoint` — `dotted`, остальные — `solid`.
- Линии рисуются под прямыми углами. Если линия идёт криво — задай стороны явно или точки `via`.

### Рецепт ручной раскладки в одну колонку

1. **Основная линия** — одна колонка по центру: `x: 470`, `w: 260`. Темы идут сверху вниз в порядке изучения,
   соединены `bottom → top`, `solid`.
2. **Подтемы** — слева (`x: 90, w: 270`) и справа (`x: 830, w: 270`), друг под другом с шагом **52 px** по `y`.
   Связь от темы: слева `fromSide: left → toSide: right`, справа `right → left`, `style: dotted`.
3. **Вертикальный ритм:** у каждой темы своя полоса высотой `max(кол-во подтем с одной стороны × 52 + 36, 110)`;
   тема стоит по центру полосы, между полосами — 34 px.
4. **Проверки и проекты** — `checkpoint` последним элементом в правой колонке темы.
5. Наверху — узел `title` с названием курса.
6. Подписи подтем — до ~28 символов (длиннее обрежется многоточием).

`npm run check` упадёт, если: узлы **перекрываются**, связь ведёт на несуществующий узел, `links` ведут на
несуществующий модуль/урок, в узле есть **неизвестное поле** (опечатка), значения не по схеме.

> [!WARNING]
> В однострочной записи `{ ... }` запятая внутри значения ломает YAML: `title: JS, Python` превратится в два поля.
> Бери такие значения в кавычки: `title: 'JS, Python и проекты'`.

## 11. Стиль текста

- **Тон — живой, неформальный, на «ты».** Как старший товарищ объясняет за ноутбуком. Шутки — можно, вода — нельзя.
- **Сначала зачем, потом как.** Каждую тему начинай с проблемы, которую она решает (лучше — из жизни хакатона).
- **Глубоко «почему».** Не «делай так», а «вот что происходит в памяти/сети/планировщике, поэтому так». Детали — в `[!DEEP]`.
- **Порциями.** Короткие абзацы, один шаг — одна идея, после теории — вопрос.
- **Код — рабочий и минимальный.** Каждый пример должен запускаться (`go run`). Не показывай код, который не компилируется,
  если это не специально (и тогда скажи об этом).
- **Задачи — от простого к сложному**, последняя задача урока — «на подумать».
- Термины: при первом упоминании — по-русски + оригинал: «горутина (goroutine)», «мьютекс (mutex)».
- **Мост от знакомого.** Ученик писал на JS/TS и Python. Новое удобно вводить через сравнение — таблица
  «Роль | TypeScript | Go» или фраза «в TS ты делал X, в Go это Y, и вот почему иначе». Отдельный подзаголовок
  «Тебе это уже знакомо» хорошо работает в начале темы.
- **Ссылки назад.** Если тема опирается на прошлый урок — ссылайся: `[слайсы изнутри](lesson:go-data/arrays-slices)`,
  на шаг — `lesson:go-data/arrays-slices#3`. Битые ссылки ловит `check`.
- **«Как спросят на собеседовании».** В конце важных уроков — блок `cards` с 3–6 вопросами.

## 12. Проверка перед коммитом

```bash
npm run check                  # всё
npm run check -- --fast        # только схемы, без запуска кода
npm run check -- --course demo # один курс
npm run dev                    # посмотреть глазами
```

`check` падает, если: YAML не по схеме; у квиза нет правильного ответа; эталонное решение не проходит тесты; git-решение не
выполняет цели; ссылки роадмапа битые. Предупреждает, если стартовый код уже проходит тесты или у задачи нет тестов.
Сборка (`npm run build`) запускает `check` первым шагом — сломанный курс не задеплоится.
